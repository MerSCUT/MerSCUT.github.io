# 原子操作与 CAS

常见的变量操作包括 :

1. __读取__ 内存中的值到寄存器
2. __修改__ 寄存器的值
3. __写回__ 内存

C++ 提供的 `std::atomic<T>` 保证了这些操作是“原子”的，即不可分割，不会被中途干扰。



无锁编程一种高级的多线程编程技术.

其核心算法通常依赖于一种特殊的硬件指令：**CAS (Compare-And-Swap，比较并交换)**。

其逻辑如下 :

1. 将变量从内存读入寄存器. 该值称为__期望值__ $A$
2. 经过一系列指令, 期望值会在寄存器中, 被修改为另一个值 $B$. 称为__目标值__. 我们希望将它写回内存.
3. __比较__ : 看内存中, 变量的值是否仍为原来的期望值 $A$ :
   1. 若是, 则用原子操作将 $B$ 值写入内存. (__交换__)
   2. 若不是, 则更新 $A$ 的值并重新计算 $B$, 重复比较过程.

说简单些 : CAS 会不断重试直到写入成功.

这个过程中,  CAS 保证 __始终留在用户态__, 不会交出 CPU 的控制权.

也就是说这种方法__不需要阻塞线程__, 也就**不需要转入内核态**造成巨大开销.

> 但是在极高竞态条件的情况下, 许多线程的 CPU 使用时间都在空转.
>
> 并且, 多核 CPU 中, 每个核都有自己的缓存. 而为了保证数据一致性 (每一个核引用的同一个内存地址的值应当一样), 会使用 诸如 MESI 的__缓存一致性协议__.
>
> 当一个核修改了内存, 其他核的缓存会__自动失效__, 只能去更慢的 L3 Cache 或内存读取新值, 这称为__缓存冲突__. 在极高的竞态条件下, 读取L3或内存的操作会反复出现, 十分占用__总线带宽__.

为了解决上述问题, 无锁编程引入了**退避策略 (Backoff Strategies)**。

- 当一个线程发现 CAS 操作失败时，==不再立即尝试下一次 CAS==，而是**稍微等待一会**，给占据资源的线程留出完成任务的时间，同时也让 CPU 缓存得到喘息。

根据退避的力度, 可以分为以下几种

| **策略名称**               | **实现方式**                  | **效果与开销**                                               |
| -------------------------- | ----------------------------- | ------------------------------------------------------------ |
| **紧凑自旋 (Tight Spin)**  | 仅仅是一个空的 `while` 循环。 | 响应最快 ⚡，但 CPU 占用 100%，最费电。                       |
| **硬件暗示 (PAUSE)**       | 使用汇编指令 `PAUSE` (x86)。  | 告诉 CPU 这是自旋锁，减少功耗并优化流水线效率。              |
| **让出时间片 (Yield)**     | `std::this_thread::yield()`   | 告知内核：“我现在没事干，先让别的线程跑吧。” 降低了 CPU 占用。 |
| **指数退避 (Exponential)** | 每次失败后，等待时间翻倍。    | 类似于网络协议（如以太网），能有效平衡延迟和系统吞吐量。     |

当然, 等少了会引入__冲突__, 等多了会引入__延迟__.

无锁编程的优化就是在寻找二者的平衡点.



# 内存顺序

在多核 CPU 的无锁世界里，为了性能，**编译器**和 **CPU** 都会==偷偷交换你的指令顺序==。

也就是说从现在开始, 可以将多核系统中的多线程程序视为类似于__GPU 的异步执行__. 我们完全不知道指令的真实顺序是什么.

但是, 一些具有同步关系的指令是不能被随意交换的. 

- 例如, 线程 A 写入内存后将标志位设为 `true`. 线程 B 只要看到标志位为 `true` 就会去读取内容. 
- 如果 CPU 为了优化性能, 将线程 A 的指令顺序调整为先设 `true` 再写入, 线程 B 就有可能读不到 A 将要写入的值, 而是读到旧值.

C++ 的原子操作引入了一个非常关键的附加参数：**内存顺序（Memory Order）**。

它的底层依靠**硬件**提供的**内存屏障（Memory Barrier / Fence）** 来拦住乱序执行。

最经典的一种结构是 `release-acquire` 语义

```C++
// 线程 A
data = 42; 
flag.store(true, std::memory_order_release); // 建立一道墙，data = 42 必须在这之前完成

// 线程 B
if (flag.load(std::memory_order_acquire)) { // 建立一道墙，读取 data 必须在这之后发生
    std::cout << data; // 绝对安全，一定是 42
}
```

上面的标志位变量 `flag` 是` std::atomic<bool>` 类型.

- `store` 成员函数中设置了内存顺序为 `std::memory_order_release`. 它指示 : 写在 `flag = true` 之前的 "写入"代码都必须先执行完, __CPU 不允许将它们交换到 `flag.store` 后面__.
- `load` 成员函数的内存顺序为 `std::memory_order_acquire`. 它指示 : 写在 `flag.load` 以后的读取内存的代码都不允许放在 `flag.load` 前面.

> 这与 Vulkan 中的__屏障__思想很像.
>
> 在录制 GPU 指令时, 可以设置 `vkPipelineBarrier`, 来实现异步执行中的指令级同步.

# ABA 问题 

看下面的场景 :

1. 线程 1 读取了一个值 **A**。
2. 线程 2 快速地把这个值从 **A** 改成了 **B**，接着又改回了 **A**。
3. 线程 1 回来检查，发现值依然是 **A**，于是觉得“什么都没发生过”，继续执行。

但在很多数据结构（比如无锁栈或队列）中，虽然值回到了 **A**，但它背后的逻辑状态可能已经完全变了（例如指向的内存已经被释放并重用了）。这会导致灾难性的内存错误。

解决这个问题最常用的方案是给指针或变量配对一个**版本号**（也叫 **Tag** 或 **Stamp**）。

- 每次变量被修改时，版本号都会**加 1**。
- 即便值从 `A` 变回了 `A`，它的版本号也会从 `1` 变成 `3`。

只有当变量值与版本号__完全匹配__时才能成功交换.



# 无锁栈

这部分是应用. 无锁栈顾名思义就是__能被多个线程使用, 且依赖无锁编程实现的栈__.

在无锁数据结构中, 我们偏爱__链式结构__. (与传统的顺序结构提供的缓存友好性不同). 后面我们会看到这种设计的优越之处.

无锁栈通常使用__头插法__链表. 头节点恰好就是 `top`, 相关的入栈出栈操作都在头部进行.

## 入栈

线程 A 试图将某个数据压入栈中. 它会执行以下几步操作 :

1. 分配一个新节点 
2. __读取`top` 值__, 并让新节点的 `next` 指针指向当前的 `top` 节点.
3. __CAS交换__ : 让 `top` 指向新节点. 
   1. 此时会触发判断. 若 `top` 已与第 2 步中读取的原值不同, 则重新执行第 2 步.
