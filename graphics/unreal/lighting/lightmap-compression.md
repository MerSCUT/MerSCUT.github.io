# RGB 的 LUVW 变换 + 压缩

当 Lightmap 压缩直接对原始的 RGB 进行非线性变换 (例如对数), 如果 RGB 通道压缩损失不同, 会导致解压后颜色产生非常明显的偏差. 

下面的代码将原始的 RGB 转换为 LUVW 格式.

- **$L$ 的计算**：公式 $L = 0.3R + 0.59G + 0.11B$ 是经典的相对亮度计算（基于人眼对不同波长光线的敏感度：绿光最高，蓝光最低，接近 sRGB / Rec.709 标准）。它提取了光照的“绝对强度”。
- **$U, V, W$ 的计算**：它们是各个颜色通道占整体亮度的比值（$U = \frac{R}{L}$ 等）。这意味着 $U, V, W$ 纯粹描述了光线的**颜色倾向（色相与饱和度）**，剔除了强度信息。 $U, V, W$ 被严格限制在一个很小的浮点区间内，非常适合映射到 $[0, 255]$ 的 8bit 整数范围内
- **逆向重构**：在 Shader 解码时，只需将压缩后的数据相乘即可无损（忽略量化误差）还原真实的 HDR 颜色：$R = L \times U, G = L \times V, B = L \times W$。

经过这种手段压缩后, 我们只需要对 $L$ 进行非线性变换即可. 即便 $L$ 存在量化误差，光照最多只会变得稍微暗一点或亮一点，但由于 $U, V, W$ 是线性或平方根存储的比例常数，**光线的颜色（RGB 的比例）绝对不会发生偏移**。

> 人眼的视杆细胞（感知亮度）远多于视锥细胞（感知颜色）。这意味着人眼对明暗交界和亮度梯度的极其敏感，而对纯粹的色度变化不敏感。
>
> 引擎通过提取 $L$，可以将最核心的计算资源（如更高精度的 Log 空间编码、残差存储通道 `Residual`）全部倾斜给亮度通道，而 $U, V, W$ 使用常规精度存储即可满足视觉要求。

```C++
static void GetLUVW(const float RGB[3], float& L, float& U, float& V, float& W)

{

float R = FMath::Max(0.0f, RGB[0]);

float G = FMath::Max(0.0f, RGB[1]);

float B = FMath::Max(0.0f, RGB[2]);



L = 0.3f * R + 0.59f * G + 0.11f * B;

if (L < 1e-4f)

{

U = 1.0f;

V = 1.0f;

W = 1.0f;

}

else

{

U = R / L;

V = G / L;

W = B / L;

}

}
```
